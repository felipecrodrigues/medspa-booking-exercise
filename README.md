# Medspa Booking API

A small Python 3.14, FastAPI, and PostgreSQL implementation of the approved medspa service and appointment API. The public business API contains exactly the eight service and appointment routes in the source exercise; `/health` is the database-aware infrastructure readiness endpoint.

## Run locally

Requirements: Docker with the Compose plugin. From the repository root, start the database and API with:

```sh
docker compose up --build -d
```

Compose waits for PostgreSQL's `pg_isready` check. The API container then applies Alembic migrations, runs the repeatable demo seed, and starts Uvicorn. The API health check calls `/health`, which executes `SELECT 1` against PostgreSQL. Open <http://localhost:8000/docs> for the interactive API documentation in OpenAPI format (generated by FastAPI) with Swagger.

The local database is available on port `5432`; the API listens on port `8000`. A persistent Compose volume retains database contents across container restarts. Stop the stack with `docker compose down` (without `-v` to retain that data).

The deterministic demo medspa is ID `1` (`Moxie Demo Medspa`) and includes:

| Service ID | Name | Price | Duration |
| ---: | --- | ---: | ---: |
| 1 | Initial Consultation | 0 cents | 30 minutes |
| 2 | Rejuvenating Facial | 12,500 cents | 60 minutes |

The seed inserts missing demo rows without overwriting existing rows. It is intended for local development, not as production data management.

## API examples

The examples assume the stack is running and that the demo seed is present. Replace IDs as needed if the persistent local database already contains records.

```sh
BASE_URL=http://localhost:8000
```

### Health

`GET /health`

```sh
curl "$BASE_URL/health"
```

### Services

`POST /medspas/1/services`

```sh
curl -X POST "$BASE_URL/medspas/1/services" \
  -H 'Content-Type: application/json' \
  -d '{"name":"Therapeutic Massage","description":"A sample massage.","price":17500,"duration":75}'
```

`GET /services/1`

```sh
curl "$BASE_URL/services/1"
```

`GET /medspas/1/services`

```sh
curl "$BASE_URL/medspas/1/services"
```

`PATCH /services/2`

```sh
curl -X PATCH "$BASE_URL/services/2" \
  -H 'Content-Type: application/json' \
  -d '{"price":13000,"duration":65,"description":null}'
```

PATCH changes only supplied fields. Omitted fields keep their stored values; in this example `description: null` clears the description to SQL `NULL`, which the response and later reads return as `null`. Explicit null for service `name`, `price`, or `duration`, or appointment `status`, returns `422` without changing the resource. An empty object `{}` succeeds as a no-op. Valid non-null values such as `price: 0` and `description: ""` are applied.

### Appointments

`POST /medspas/1/appointments`

```sh
curl -X POST "$BASE_URL/medspas/1/appointments" \
  -H 'Content-Type: application/json' \
  -d '{"start_time":"2035-01-15T10:00:00-06:00","service_ids":[1,2]}'
```

The response includes the booking-time service snapshots and totals derived from those snapshots. A newly created appointment has status `scheduled`.

`GET /appointments/1`

```sh
curl "$BASE_URL/appointments/1"
```

`PATCH /appointments/1`

```sh
curl -X PATCH "$BASE_URL/appointments/1" \
  -H 'Content-Type: application/json' \
  -d '{"status":"completed"}'
```

`GET /appointments`

```sh
curl "$BASE_URL/appointments"
```

Missing medspas or records return `404`; invalid request fields, time values, and service selections return `422`. Database unavailability returns `503` from `/health`.

## Tests and schema

Install the Python 3.14 environment and run unit tests and static checks:

```sh
uv sync --python 3.14
uv run --python 3.14 pytest -q
uv run --python 3.14 ruff check src/medspa_booking tests alembic
```

PostgreSQL integration tests use a dedicated disposable database and never SQLite. Start the optional test database service in another terminal:

```sh
docker compose --profile test up -d test-db
```

Then run the full suite with its explicit test-only URL:

```sh
TEST_DATABASE_URL='postgresql+psycopg://booking:booking@localhost:55432/medspa_booking_test' \
  uv run --python 3.14 pytest -q
```

Before it resets `public`, the test fixture requires a PostgreSQL database ending in `_test`, a loopback host (`localhost` or a loopback IP), and a URL with no query parameters so driver options cannot override the validated target. Unit tests remain runnable without the test database; PostgreSQL-dependent tests are then skipped.

Reviewable PostgreSQL DDL is in [`sql/schema.sql`](sql/schema.sql). It is generated from SQLAlchemy metadata with:

```sh
uv run --python 3.14 python -m medspa_booking.db.schema_ddl
```

The migration is kept in [`alembic/versions/`](alembic/versions/) and integration setup exercises it against PostgreSQL.

## Assumptions

- Prices are integer cents in `0..2147483647`; durations are integer minutes in `1..2147483647`. Service names must contain a non-whitespace character, and descriptions may be omitted or null when creating a service.
- Appointment start times must include an explicit timezone offset and be later than request-validation time. Responses normalize start times to UTC.
- Path IDs and appointment `service_ids` are positive PostgreSQL `INTEGER` values. Request bodies reject unknown fields.
- An appointment must select at least one distinct service owned by the path medspa. Invalid selections fail before appointment or association rows are written.
- Appointment totals are calculated from the service price and duration captured when booking; later catalog updates do not alter the stored snapshots or totals.
- New appointments default to `scheduled`. Only `scheduled`, `completed`, and `canceled` are accepted, with free transitions among them.
- PATCH preserves omitted fields, while supplied non-null values are validated and applied. Sending `description: null` clears a service description; sending null for service `name`, `price`, or `duration`, or appointment `status`, returns `422` without changes. An empty `{}` PATCH body is a no-op.
- Lists return all matching rows in ascending primary-key order. There is no pagination or filter surface.

## Scope decisions

- Only the eight listed service and appointment routes are implemented. Medspa records are supplied by the local seed for now (ID=1), considering the list of provided routes was final and intentionally left the Medspa CRUD operations out of scope – which can make sense if this is an external, client-facing booking only API to be used by the clients, not allowing them to create a new Medspa instance and only allowing them to use the referred IDs.
- The endpoint `GET /appointments` used to list all appointments does not filter by Medspa, and there are actually no endpoints to list all appointments from a single Medspa. This was intentionally kept as requested, but the implementation of a `GET /medspas/{medspa_id}/appointments` would be helpful.
- Availability, business hours, provider scheduling, overlap checks, and status transition restrictions are not implemented.
- Authentication and authorization were not implemented as of now, so any user has access to all endpoints and can make any changes.

## Open business decisions

- **Appointment status transitions:** The API accepts `scheduled`, `completed`, and `canceled` and currently permits transitions among all three statuses; it does not enforce a lifecycle policy. The team should decide whether a completed appointment may be canceled, whether a canceled appointment may be completed or restored, or whether only `scheduled → completed` and `scheduled → canceled` should be allowed. Any agreed transition policy can then be added consistently to the API and persistence layer.
- **Appointments already in progress:** The current API rejects appointment start times that are not in the future. A real-world case to discuss is a customer asking for additional services after their originally booked procedure has started. The team should decide whether this should be supported as a separate in-progress appointment amendment and what validation or permissions it needs. This exercise does not allow arbitrary past appointment bookings; a future implementation could add a narrowly scoped, explicitly authorized workflow for mid-session additions.

## Tradeoffs

- Synchronous SQLAlchemy 2 and psycopg keep the single-database service straightforward; synchronous FastAPI handlers run in its worker pool.
- The appointment/service association is an explicit table because it stores booking-time snapshots. Totals are derived from those rows rather than stored a second time and risking drift.
- SQLAlchemy metadata is the schema source of truth; the reviewable PostgreSQL DDL is generated from it, while Alembic provides repeatable runtime upgrades.
- Local PostgreSQL credentials are intentionally simple for development only. Do not reuse them in a deployed environment.

## Scope Change Scenario
A PM pings you late in the build:

> “Can we add a customer_notes field to appointments so customers can leave special instructions?”

Before implementing it, I would clarify whether the note should apply to the entire appointment, to each service in an appointment, or both. If I could not get an answer before making a decision, I would proceed with one optional, appointment-level field and document that assumption.

### What would I change in my implementation?

The change is relatively contained, but it affects the database, API schemas, operations, routes, tests, and generated DDL:

1. I would add a nullable `customer_notes` column to the `Appointment` model. Its type annotation should reflect that it can be null, for example `Mapped[str | None]`. I would also confirm a maximum length and whether notes should be plain text; 2,000 characters is an assumption, not a confirmed requirement.
2. I would update the appointment create and response schemas so clients can submit and receive the field. If customers should be able to edit notes after booking, I would also add it to the PATCH schema.
3. I would define PATCH behavior explicitly: omission preserves the existing note, a supplied string replaces it, and `customer_notes: null` clears it. That matches the API's nullable-field semantics; null for non-nullable fields remains a `422` error.
4. I would update appointment operations and routes to pass the field as a normal value, keeping Pydantic request objects at the HTTP boundary.
5. I would write tests first for creating appointments with and without notes, reading and listing appointments, and updating or clearing notes if PATCH is in scope. I would also test the length limit and migration behavior. This API has no DELETE endpoint, so I would test its supported operations rather than describe them as full CRUD.
6. I would create a **new Alembic migration**, review the generated migration, and test it against the dedicated test database. Since the column is nullable and has no default, existing appointments would have a null value. I would regenerate `sql/schema.sql` from the ORM metadata and verify the DDL and migration remain consistent.
7. Because special instructions may contain sensitive personal information, I would confirm who can view or edit the notes, avoid putting their contents in logs, and agree on appropriate retention and access controls.

### How would I communicate and handle this in a real scenario?

The first step would be to understand how critical is this feature: can we go live without it and deliver it with the next build, or should it be part of our MVP? I would discuss the risks of making changes late in the build, and try to understand if we have any hard external date commitment; let's say this will take one extra day: did we promise to deliver the original set of requirements today for one of our customers? Or maybe we have already agreed on delivering this new improved version with the new customer_notes field by tomorrow. Then, I'd proceed to evaluate the complexity of implementing the new feature, and weigh the pros and cons of doing it immediately or not considering the rest of our roadmap/sprint targets.

If we agree that it has to be part of the current delivery cycle, I would then quickly evaluate the current team status and workload to find out if I'm the best available engineer to work on this, or if there is anyone else with a better workload that could take care of it with less impact on the team's deliverables. Next, I'd make sure our current planned build is still proceeding as originally planned, as a safeguard in case we discover this new feature is more complex than expected and requires more time so we still have the original build ready to go; this would also be useful if we deploy the new version and note some issues with the new customer_notes field, we can still go back to the originally planned build with minor impact. 

Finally, for the implementation, I'd evaluate the requirements, clear out any questions (as the one mentioned above about which scope should we add notes, one per appointment or one per service in the appointment, max string length, etc.). With all this ready, I'd proceed with the implementation and pack a separate build with a minor version bump to have another level of guardrail. After deployment, I'd save some time to run queries (e.g. how many appointments have data in the customer_notes field) and understand how much this new field is being used to understand if we made a good or a bad choice, strictly for internal team and process improvements.

## AI usage

THe first usage of AI was to help with the two test projects I had as part of the learning step, familiarizing myself with the language and frameworks before starting the implementation.

For the project itself, I first converted the requirements PDF into a Markdown source document for the agents to use as shared knowledge for the project context. I then wrote an orchestration prompt defining the exercise scope and directing the work to use OpenSpec for spec-driven development; FastAPI, PostgreSQL, SQLAlchemy, Alembic, Pydantic, and Docker Compose; an ontology for domain and evaluation concepts; a proportionate, feature-oriented architecture; and TDD with unit and PostgreSQL integration tests. 

The prompt also assigned an orchestrator to coordinate specialized subagents for planning/specification, implementation, independent quality and correctness review, operational validation, and evaluation of each agent's input and output with a grading system. Each agent ran in a different model based on the needs of each agent and what each model excels at.and also for token management. Running different model families also helps exposing the codebase to different points of view, which in my personal experience has been showing good results then when all agents run in the same family.

I have not used AI for:
- Understand the requirements or make high impact business decisions. I thoroughly reviewed the initial requirements document, evaluated pros and cons of each business and technical decision, and had the final word for all the functional and non-functional requirements. After the end of each loop, I checked the decisions, the evaluation outcomes, the code itself, test quality, and made new prompts to adjust the outcomes.
- Write the prompts (meta-prompting): all the agentic workflow was manually defined by me, and the prompts used to build the goals of the project were manually written.
- Identify open business decisions and scope decisions that would require discussion with the team before implementation.
- Answer the "scope change scenario" part of the exercise.
