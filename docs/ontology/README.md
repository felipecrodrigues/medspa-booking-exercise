# Medspa Booking Ontology

This ontology describes the medspa booking domain in the Moxie backend take-home exercise and the traceability/evaluation evidence used to assess its implementation and AI contributions. It captures Medspa, Service, Appointment, booking-time service snapshots, status, endpoint contracts, source requirements, OpenSpec decisions, agent runs, input/output quality observations, and evidence. User-approved API and booking policies are represented; implementation-specific error and migration details remain in OpenSpec.

## Files

- `core.ttl` — reusable repository and evidence vocabulary.
- `extensions/medspa-booking.ttl` — medspa, service offering, appointment, selection, and status vocabulary.
- `extensions/exercise-evaluation.ttl` — requirements, open questions, decisions, agents, metrics, and evidence vocabulary.
- `shapes/` — SHACL contracts for the stable data model, endpoint requirements, and future evaluation observations.
- `examples/example-data.ttl` — illustrative domain data, all eight explicitly listed endpoint contracts, and representative open questions.
- `medspa-booking.owl` — consolidated RDF/XML OWL export generated by the validator; the Turtle modules remain the editable source of truth.
- `scripts/validate.py` — isolated SHACL validation and OWL export script.

## Modeling decisions and limits

- Logical entities use stable IRIs. If repository state is later captured per commit, model it as a `core:CommitSnapshot` linked with `prov:specializationOf`; do not change a logical entity's IRI for each revision.
- OWL describes concepts and relationships. SHACL carries the instance-level cardinality and datatype rules.
- The ontology is kept within OWL 2 RL-friendly constructs; no OWL cardinality restrictions or complex class expressions are used.
- Appointment totals are modeled as sums of booking-time service price/duration snapshots, so later catalog changes do not rewrite historical totals.
- Appointments select at least one distinct service from the same medspa. Start times require an explicit timezone and must be in the future; availability, business hours, and overlap rules remain out of scope.
- Only the eight explicitly listed service and appointment routes are in scope. Medspa records are supplied as demo/seed data or documented database setup; no medspa CRUD or delete routes are added.
- The approved evaluation format is versioned JSONL with 1–5 input/output quality ratings, rubric dimensions, evidence references, and explicit unavailable values. Metric observations link the agent run, rubric definition, quality dimension, and evidence. The concrete rubric is documented in `docs/eval/README.md`.
- The authorized Scope Change Scenario response is recorded as a decided, design-only proposal. It does not change the implemented API scope.
- Example data is illustrative and does not establish additional business policy.

Instance graphs may also be serialized as JSON-LD 1.1 for agent-facing payloads, using these same IRIs. SPDX or CodeMeta terms can be referenced later if license or software bill-of-materials metadata is added; they are not needed to model the current business domain.

## Validate and extend

Run from any working directory:

```bash
python3 docs/ontology/scripts/validate.py
```

The script creates an isolated environment under `docs/ontology/.venv/`, loads all Turtle ontology, shape, and example files, validates the example graph with RDFS inference, and refreshes the RDF/XML export when the graph conforms. It requires Python 3.9 or newer. The API runtime is Python 3.14 as selected by the user.

To extend the model, add a focused module under `extensions/`, add its SHACL shapes under `shapes/`, update `examples/example-data.ttl`, then run validation. Record any business or evaluation policy change in OpenSpec before treating it as an implementation requirement.
